# 仓库维护规范

适用于 `mentho7/gloam-cn`。贡献入口是 [CONTRIBUTING.md](../CONTRIBUTING.md)，发布操作以 [RELEASE.md](../RELEASE.md) 为准。

## 分支与审查

- `main` 是集成基线；从最新 `origin/main` 建立短期分支，以 PR 合入。人工分支使用 `feat/`、`fix/`、`docs/`、`chore/`；代理分支使用 `codex/`，后接具体主题。不要以版本号代替工作主题。
- 一个 PR 解决一个问题，写明触发条件、行为变化、验证结果和局限。有关联 Issue 时用 `Closes #编号`；尚未完成的问题使用 `Refs #编号`。
- 默认 squash merge，PR 标题使用 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`build:`、`ci:` 或 `chore:`。破坏兼容的变更使用 `!` 并说明迁移办法。提交正文解释原因，保留贡献者归属。
- 合入前检查最终差异、CI 的 `validate` 和 `build` 结果，以及未解决的审查意见。单人维护时也通过 PR 留下自审和验证记录，不声称完成了独立审查。
- 合并后可删除已合并的短期远端分支。清理历史分支前检查未合并提交、关联 PR 和工作区；不得批量删除不明用途分支或改写共享历史。
- 同步上游时使用独立 PR，说明上游提交范围、冲突处理、本 fork 的差异及回归验证；保留 MIT 许可和第三方声明。

## Issue 与版本计划

缺陷、功能和跨 PR 的规格存放在本仓库 GitHub Issues，不再另建一份易过时的待办文档。小型文档修正可以直接提交 PR。

遵循 [分流标签](agents/triage-labels.md)：新问题为 `needs-triage`，等待信息添加 `needs-info`，边界明确后进入 `ready-for-agent` 或 `ready-for-human`。拒绝的问题说明原因后标记 `wontfix`。`bug`、`enhancement` 等是分类，不替代分流状态。

需要安排发布时创建 `vX.Y.Z` milestone，写出交付范围与验收条件；只纳入已接受的工作。日期未知时不编造截止日期，未完成的条目显式延期，发布验证完成后再关闭 milestone。

## 版本与文档

- 版本采用 `MAJOR.MINOR.PATCH`：不兼容的数据、配置或 CLI 契约变化提高主版本；兼容的新功能提高次版本；兼容修复提高补丁版本。纯维护提交不自动发布新版。
- 发布准备 PR 同时修改 `src/Gloam/Gloam.csproj` 的 `<Version>` 和对应 `docs/release-notes/vX.Y.Z.zh-CN.md`（兼容既有 `.md` 文件）。标签、项目版本和说明必须一致。
- 当前流水线只支持稳定版 `vX.Y.Z`；预发布需要先实现并验证独立更新通道，不能把 `-rc` 直接推入稳定更新源。
- 已发布标签不可移动或复用。继承的上游标签不等于本 fork 发布过这些版本；本 fork 的发布索引见 [CHANGELOG.md](../CHANGELOG.md)。
- README 服务于安装与使用；贡献指南服务于开发；维护规范服务于协作；发布手册服务于发版。避免在多处复制同一操作步骤。
- 变更用户行为时同步中英文 README、相关使用文档及发布说明。发布说明记录升级影响、兼容性、校准影响、已知问题和实际验证，不把“未测”写成“通过”。
- `site/whitepaper.html` 是白皮书源文件；Markdown 由脚本生成。领域词汇与架构决策沿用 [单一上下文规则](agents/domain.md)。
- 勘测记录必须带日期与适用提交；旧日志只证明当时的构建。当前规范优先于历史记录，不把本机路径作为读者必需的证据。

## GitHub 设置与实际限制

维护者应配置：PR 合并、成功的 `validate` / `build` 检查、解决审查讨论、禁止强推和删除 `main`、保护发布标签。团队有独立审查者后再要求至少一次批准。签名发布使用 `release` environment，并限制发布来源。

2026-11-03 检查时仓库为 **private**；rulesets API 返回 HTTP 403，提示需要升级 GitHub 套餐或公开仓库。这些保护要求目前不能视为已经在服务端强制执行。升级后按实际检查名称配置并验证；不为启用规则而擅自公开仓库。

同次检查中三个合并方式都开启，合并后自动删除分支关闭。本文的 squash 与分支清理约定是维护流程，不代表远端设置已修改。

客户端不携带 GitHub 凭据，私有仓库不能用作匿名安装下载或自动更新源。继续私有开发时，应另行设计公开分发渠道；在此之前不要承诺自动更新可用，也不要把仓库令牌打包进应用。
